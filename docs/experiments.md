# 实验记录：2D 分支定界 + 3D 验证

目标：在每个 query 耗时不超过 3 s 的约束下尽量提高成功率（阈值不变：水平 0.2 m、yaw 2°）。所有数字来自同一台机器（Linux，Intel Xeon 2.1 GHz × 4 核，原生 Release 编译，OpenMP 4 线程），基线由同一台机器上的原始提交重新编译运行。

## 结论

| 数据集 | 基线成功 | 基线 query 中位 / 最大 | 新方案成功 | 新 query 中位 / 最大 | 单线程 中位 / 最大 |
|---|---:|---:|---:|---:|---:|
| 合肥 hefei（公开） | 20/38 | 1.30 / 1.71 s | **37/38** | 0.10 / 0.16 s | 0.23 / 0.54 s |
| 伏牛 funiu（公开） | 3/20 | 4.14 / 7.26 s | **15/20** | 0.29 / 0.59 s | 0.60 / 1.39 s |
| anhui（补充，与合肥同图） | 11/20 | 1.42 / 1.72 s | **18/20** | 0.10 / 0.24 s | 0.22 / 0.51 s |
| beijing（补充） | 7/12 | 4.03 / 4.65 s | **12/12** | 0.61 / 1.63 s | 1.65 / 1.81 s |
| niuniu（补充，温室） | 5/13 | 7.64 / 8.77 s | **9/13** | 1.58 / 2.14 s | 2.32 / 2.67 s（6/13） |
| 合计 | 46/103 | | **91/103** | | |

- 103 个 query 中**没有任何一例**由基线成功变为失败（逐例表见文末）。
- 所有 query 在 4 线程和单线程下都低于 3 s。单线程时 niuniu 会触发分支定界时间预算，成功数降为 6/13，其它数据集不变。
- 建库耗时（不计入 query）：合肥 0.27 s、伏牛 0.82 s、beijing 0.89 s、niuniu 1.8 s（基线分别为 8 s、32 s、28 s、92 s）。

补充数据集只用于验证泛化和取舍，没有提交进仓库。

## 方法

1. **局部地面与结构带**：地图按 1 m 栅格取每格 5% 分位高度，再在 3 m 邻域取最小作为局部地面；地面以上 0.3–2.0 m 的点视为“结构”（墙、柱、家具）。query 先用 RANSAC 拟合地面并调平（容忍机器人 roll/pitch），再按同样的高度带取点，并做 0.2 m 的 2D 体素均值。
2. **全局 2D 搜索**：结构点建 0.1 m 似然场（σ = 0.2 m），用多分辨率 max 金字塔做分支定界，覆盖全图所有平移 × 360 个 yaw，结果与穷举等价。只在“观测到地面的格子（膨胀 1 m）”内找机器人位置。叶子按 (x, y, yaw) 分桶后做 NMS，保留 ≥ 0.9 × 最优分的不同候选（最多 128 个）。
3. **3D 预筛**：重复场景里（温室、长走廊）2D 带的区分度不够。对每个候选，用地面以上全部 3D 点在地图占据位图（0.2 m，膨胀 1 格）中的命中率，在 (x, y, yaw, z) 上坐标下降爬山，然后按命中率重排。
4. **GICP 验证与精修**：预筛前 6 名（得分 ≥ 0.9 × 最好）各做一次粗 GICP（对应距离 1.0 m），按 0.2 m 内点率选择。胜出者只用 10 m 内的点做一次精 GICP（0.3 m）；若修正超过 0.6 m 则保留粗结果。GICP 目标协方差在建库时预先算好，这是基线每个 query 都要重算的主要耗时。
5. **时间预算**：分支定界上限 1.5 s，超时返回已找到的最好候选；累计超过 2.2 s 后不再开始新的 GICP 验证。

参数敏感性（当时的版本，合肥 / 伏牛）：σ 0.15/0.3、高度带 0.2–1.5 或 0.5–2.5、yaw 步长 2°、scan 体素 0.3、GICP 体素 0.3 下都是 37/38、12/20，结果没有落在参数刀刃上。

**试过但没有采用：**

- **射线空闲负证据**（query 射线穿过的地方若在地图里被占据则扣分，含按高度分层的版本）：beijing 12→9，niuniu 6→5，分支定界慢 3–5 倍。
- **预筛爬山加入 roll/pitch**（为 anhui q11 的坡道）：没有修好 q11，niuniu 9→5。
- **全局缩短 query 量程到 10–15 m**：funiu 提高，但合肥 37→36。最终只在精修阶段用近处点。

## 仍未解决的失败

- **伏牛 5 例 imprecise（0.21–0.24 m）**：地图与真值不一致，不是算法收敛差。所有 20 个 query 的估计相对真值都是 map 系下 dy ≈ −0.15…−0.24 m、dx ≈ 0、yaw ≈ +0.5°，与机器人朝向无关，且 dy 随 x 线性变化（约 0.01 m/m），等价于真值相对地图约 0.55° 的整体旋转。从真值出发分别只用近处、远处、墙、天花板、地面点做点到面 ICP，都收敛到同样的偏移。精修只用 10 m 内的点把成功数从 12 提到 15，并在三个补充数据集上不变（无负面影响）；但这个选择是在看过伏牛真值之后做的，有对公开集过拟合的风险，可通过 `fine_max_range: 0` 关闭。
- **合肥 q16（wrong_place）**：query 只看到 5.8 m 内的两面平行墙（窄走廊），地图里有多处等宽走廊，2D 和 3D 得分都无法区分，属于观测本身的歧义。
- **anhui q11（imprecise，yaw 14°）**：机器人在约 9° 的坡道上（真值 pitch −8.8°，z 比主地面高约 1 m）。调平假设脚下地面水平，初值偏差过大，GICP 收敛到错误的局部极值。
- **anhui q08（imprecise，1.4 m）**：沿走廊方向的平移退化。
- **niuniu q07、q08**：温室过道两端和种植行高度重复，错误位置的 3D 内点率（0.90–0.91）与真值（0.92）只差约 1%。
- **niuniu q12、q13**：真值附近的 2D/3D 得分都很低（q13 真值处 2D 得分 0.17），query 与地图重叠很少，地图可能不覆盖或现场变化大。
